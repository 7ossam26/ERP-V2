B.1 — pos-discount.md

B.1.1 Math / rounding

IDSevFindingResolutionStatus
1.1.aHIGH Rounding rule inconsistent between backend total, POS totals, and receipt. Line-rounded values can diverge from backend total by ±1 EGP. Lock the rule: carry full precision through all intermediate computations; round only (a) persisted discountAmount and (b) final total. Receipt renders the backend-computed total verbatim; tax line shows the unrounded value rounded for display only. SPEC-UPDATED
1.1.bHIGH §4.4 refund formula is mislabeled. "Proportional refund of the discount" does not match the code. Rewrite §4.4: proportional_discount_share = round1(lineSubtotal * discount_amount / original_subtotal); refundAmount = lineSubtotal − proportional_discount_share. Algebraically identical; matches the spec wording. SPEC-UPDATED
1.1.cMED §4.4 references original_subtotal; no such column defined. Existing sales.subtotal semantics unclear. Confirmed: sales.subtotal is stored pre-discount. Spec now states this explicitly; refund formula uses sales.subtotal as original_subtotal. SPEC-UPDATED
1.1.dHIGH Tax computed on post-discount subtotal changes tax_amount on the sale. May break statutory VAT treatment. Needs a finance/legal call. Plan now flags this as an open decision; default keeps current "tax on post-discount" behavior until finance weighs in. If the answer changes, formula moves to tax = subtotal * taxRate (pre-discount) and receipt shows the discount as a post-tax concession. DECIDE

B.2 — call-center-design.md

B.2.1 Concurrency

IDSevFindingResolutionStatus
2.1.aHIGH §6.4 NEW → PREPARING is not atomic. Two cashiers can both claim; last write wins silently. Spec now requires conditional update: UPDATE orders SET status='PREPARING', claimedById=?, claimedAt=NOW() WHERE id=? AND status='NEW'. Check affectedRows == 1; otherwise return 409 ALREADY_CLAIMED. Integration test required. SPEC-UPDATED
2.1.bHIGH §6.2 shift-open drain fires for the opening user only. D6 says broadcast to all open-shift cashiers; the two rules contradict. Drain broadcasts to all currently-open shifts at the branch via the EventBus. Clients dedup by Order.id. D6 is authoritative; §6.2 text updated to match. SPEC-UPDATED
2.1.cMED §6.6 cancel transaction partial-failure semantics not explicit. Cancel wraps Inventory credit + Order.status='CANCELLED' + Sale update in a single Prisma $transaction. Add an integration test that injects a failure after inventory credit to verify full rollback. SPEC-UPDATED

B.2.2 Schema / migration

IDSevFindingResolutionStatus
2.2.aMED §5.2 backfill "create Order row for every existing Sale" can lock the table on large history. Backfill runs in 5,000-row batches with a short sleep between batches; scheduled during the next maintenance window. Migration file documents the batching approach. SPEC-UPDATED
2.2.bMED Sale.branchId and Order.branchId can drift. Drop Order.branchId; always join through Sale. Indexes [channel, status, branchId] replaced by [channel, status] + join filter, with a compound index on Sale(branchId, id). Schema section rewritten. SPEC-UPDATED
2.2.cLOW Notification.payload is Json, not indexable for "high-value order" filters. Deferred. Current filters (userId, readAt) are enough for v1. Schema will extract total to a column when an indexed filter is first requested. DEFER

B.2.3 SSE / real-time

IDSevFindingResolutionStatus
2.3.aHIGH §6.3 SSE auth uses JWT in URL query string — leaks through proxy logs, history, Referer. Replaced with a single-use stream-ticket pattern: POST /api/events/ticket (authed) returns a 24-byte base64url token, 30s TTL, consumed on first use. GET /api/events/stream?ticket=... validates + deletes. Long-lived JWT never travels in a URL. Implemented in Part A.3. FIXED
2.3.bMED Last-Event-ID replay against a 30-day-TTL Notification table: reconnect after > 30d silently misses events. On reconnect, if lastEventId < MIN(Notification.id), server emits a synthetic replay-truncated event. Client handles it by refetching state via REST. Added to §6.3 and §8 edge-cases. SPEC-UPDATED
2.3.cLOW Heartbeat every 25s — Cloudflare Free closes idle at 100s. 25s is below that cap; no change. Noted: if deployment target changes to a different proxy, revisit interval. Documented inline in §6.3. SPEC-UPDATED

B.3 — bulk-pos-design-doc.md

B.3.1 Stored aggregates

IDSevFindingResolutionStatus
3.1.aHIGH BulkOrder.paidAmount / balanceDue are stored columns with no single write path — silent drift risk. Pick option 2: every BulkPayment create/void/refund goes through a bulkPaymentsService that also recomputes paidAmount and balanceDue in the same transaction. Daily reconciliation cron asserts paidAmount == SUM(non-voided payments) and alerts on mismatch. SPEC-UPDATED
3.1.bMED getOpenBalance clamps to 0 with Math.max, hiding over-payment. Remove the clamp. Allow negative balances; surface as a "credit on file" badge on customer detail. Function now returns a signed number; callers (credit check, statement) handle both cases. SPEC-UPDATED

B.3.2 Numbering

IDSevFindingResolutionStatus
3.2.aMED §4.4 issues BULK-RCP-NNNN but §3.7 has no RECEIPT sequence. Add a RECEIPT key with prefix BULK-RCP- to BulkNumberSequence seed. §3.7 updated. SPEC-UPDATED
3.2.bMED Atomic counter: "FOR UPDATE or retry loop" is ambiguous. Pick SELECT … FOR UPDATE inside prisma.$transaction at the MySQL default REPEATABLE READ isolation level. Retry-loop variant dropped. bulkNumbering.service.js contract documented. SPEC-UPDATED
3.2.cLOW No sequence for PROFORMA, but BulkDocument.documentNumber is unique. Proformas get their own sequence PROFORMA with prefix BULK-PF-. A BulkDocument row IS written when a proforma PDF is requested; subsequent requests for the same draft reuse the existing row. §3.7 + §4.3 updated. SPEC-UPDATED

B.3.3 Credit limit

IDSevFindingResolutionStatus
3.3.aHIGH Confirm doesn't know the payment method yet (payments recorded separately), yet spec says "check if CREDIT". At confirm, assume worst case: add the full total to open balance and reject if it exceeds limit. Every subsequent POST /payments recomputes; if a cash payment brings open balance below limit, no further action. Removes the ambiguity. SPEC-UPDATED
3.3.bLOW assertCreditLimitOk(tx, customer, projectedOrderTotal) signature doesn't admit split payments. Contract now: caller is responsible for computing projectedOrderTotal (worst-case unpaid portion). Service docstring updated. No signature change. SPEC-UPDATED
3.3.cMED "Cash refund pays out but doesn't reduce open AR" — easy to misread. Added three worked numeric examples to §4.5 (full refund of paid order, partial refund of partially-paid order, credit note against unpaid order). Each walks through ordersSum − paymentsSum − refundsSum to show the resulting open balance. SPEC-UPDATED

IDSevFindingResolutionStatus
